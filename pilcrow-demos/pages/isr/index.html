ISR Incremental SSR

Stale-while-revalidate page caching. load() only runs on a cache miss or background revalidation — not on every request.

Plain English: ISR works like a notice board. Someone writes up the board once, and everyone who walks past reads the same notice — until enough time has passed and someone updates it. The board is never blank while the update is happening; visitors keep reading the old notice until the new one is ready.

Key insight: REVALIDATE is not a timer that pushes updates to open browser tabs. It is the minimum age at which the next incoming request is allowed to trigger a fresh render. A tab already showing the page will not change on its own — users must reload or navigate.

Reload within 2 seconds → same values (cached). Reload after 2s → same values served instantly, but load() fires in the background. Next reload shows the fresh values.

Configuration: REVALIDATE = 2 (2-second TTL for this demo), MAX_STALE = 10 (serve stale for up to 10s past TTL), CACHE_TAGS = ["demo-isr"] (for manual invalidation). All three are pub const declarations stripped at codegen time — they never appear in generated Rust.
When should I use ISR? (click to expand)

ISR is the right model when all three of these are true:

  • The page content comes from a database, API, or file — not from request-specific data like session or cookies.
  • The content changes occasionally (minutes to hours), not on every request and not truly in real-time.
  • Many users will request the same URL, so caching one render and sharing it across requests saves real work.

Good fits:

Page typeWhy ISR worksSuggested REVALIDATE
Blog post / articleContent rarely changes; popular posts get heavy traffic300–3600s
Product pagePrice/stock change infrequently; bust cache on inventory update60–600s + tag bust
Marketing / landing pageEdited once in a while; identical for every visitor3600s+
Dashboard summary / statsSlightly stale is acceptable; live counters not needed30–120s
Documentation pageChanges on deploy only; use cache-tag bust on release86400s + tag bust

Bad fits — use a different model instead:

SituationProblem with ISRBetter model
User-specific pages (profile, cart, inbox)Cache would be shared across users — security riskSSR (no cache)
Live price ticker, chat, live scoreISR won't push updates; users must reload to see changesSSE / WebSocket
Page reads from cookies or auth headersCached response ignores per-request contextSSR (no cache)
Data changes on every request (e.g. a counter)Counter increments only on revalidation, not every visitSSR (no cache)
The timestamp / counter trap: if you render Date.now() or a request counter inside an ISR page, users won't see it update on every reload — only when a background revalidation fires. For live values, fetch them client-side (polling, SSE) instead of baking them into the server-rendered HTML.
