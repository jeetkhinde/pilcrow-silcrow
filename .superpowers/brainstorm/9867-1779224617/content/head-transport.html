<pilcrow:head> on Fragment / JSON Nav

The server knows each page's <pilcrow:head> content at render time. How should it travel with a fragment response so the client can update <title>, meta tags, etc.?

For a full navigation, the head is already in the HTML. For fragment/JSON nav, the body is swapped but <head> is not touched — so <title> and meta tags go stale unless we explicitly push updates.

A

Inline <template data-ps-head>

Codegen prepends a hidden <template data-ps-head>…</template> to every page body. For fragment responses, Silcrow extracts it before injecting the slot and applies each child node to document.head (replacing same-keyed nodes by name/property).

Pros

  • Zero new endpoints
  • Full-page responses carry it too — one code path
  • Inspectable in DevTools

Cons

  • Adds a small hidden element to every page body
B

Separate response header X-Pilcrow-Head

Server encodes the head content as JSON in an X-Pilcrow-Head response header. Silcrow reads it and applies to document.head after the swap.

Pros

  • Fragment body is clean — no hidden elements

Cons

  • Headers have size limits — breaks with large head blocks
  • HTML in a header needs escaping
C

Named slot in rendered body: data-ps-slot="head"

Codegen wraps the rendered <pilcrow:head> output in a live <div data-ps-slot="head" hidden> at the top of <body>. Fragment nav replaces this slot too. Silcrow reads it and mirrors into document.head.

Pros

  • Same slot mechanism as main content
  • Persistent — always available after load

Cons

  • Slightly heavier — hidden div always in DOM

Note — what "applies to document.head" means

Silcrow would: set document.title, upsert <meta name="description"> by name/property attribute, replace <link rel="canonical">. It would NOT remove head nodes that weren't in the new head — to avoid breaking analytics scripts etc.
