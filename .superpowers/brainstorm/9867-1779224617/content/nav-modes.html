Slice D — Three Navigation Modes

How should s-boost navigation decide which mode to use?

The plan says the mode is driven by an X-Pilcrow-Layout response header. That means the server decides on each response. The client uses whatever the server says.

Here's what each mode means in practice:

MODE A — FULL
Page
Nav
Entire body replaced
  • Whole <body> swapped
  • Nav re-rendered from response
  • Current behavior today
  • Scroll → top
MODE B — FRAGMENT
Page
Nav (preserved)
Only main slot replaced
  • Only data-ps-slot="main" swapped
  • Nav, sidebar stay alive
  • Server sends fragment HTML
  • Scroll → main-top
MODE C — JSON
Page
Nav (preserved)
Atoms patched in-place
  • Server returns JSON props
  • Silcrow patches bound elements
  • Zero HTML re-render
  • Scroll preserved

How the server signals the mode: the server sets X-Pilcrow-Layout: fragment or X-Pilcrow-Layout: json on the response. No header = full (current default).

Key question: Does the client need to tell the server what layout it has (so the server can decide intelligently), or does the server always know from the route?

A

Client sends layout hash

s-boost adds X-Pilcrow-Layout: <hash> to the request. Server compares hashes — if same layout, returns fragment/JSON instead of full. Enables smart same-layout shortcutting.

B

Server always decides, no client hint

Routes declare their layout; the server knows at render time which mode is appropriate. Client sends a plain request, gets the mode in the response header. Simpler — no hash negotiation.

C

Client requests a mode

s-boost sends X-Pilcrow-Nav: fragment on every boosted request. Server honours it if it can. Explicit opt-in per request rather than per route.
